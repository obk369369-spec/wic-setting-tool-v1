# WIC 고객 안내 대화창 통합 공통마스터 — VERIFIED FINAL LOCK

## 0. 완료 판정 잠금
이 문서는 모든 분야 고객 안내·추천자료·메일 문안·중간안내서·최종안내서의 유일한 공통마스터다.

- `FINAL`, `LOCK`, `통합 완료`는 문구가 아니라 검증 상태를 뜻한다.
- 과거 관련 규칙 수집 → 항목별 대조 → 본문 반영 → GitHub 재조회 → 누락 0 확인이 끝나기 전에는 완료라고 표시하지 않는다.
- 사용자가 한 번 지적한 실패 유형은 즉시 이 문서에 흡수하고 같은 오류를 다시 사용자에게 확인시키지 않는다.
- 새 규칙은 별도 고객 안내 규칙문서를 만들지 않고 이 문서에만 통합한다.
- 최신 사용자 직접 지시가 항상 최우선이다.

## 1. 규칙 우선순위
1. 사용자의 가장 최근 직접 지시·제외·허용 조건
2. 이 `UNIFIED_CUSTOMER_GUIDANCE_RULES.md`
3. 공통 고객 DB·발송이력·거래 발행사 데이터
4. 과거 분야별 지시문·대화기록·구버전 문서

## 2. 역할 경계
멘트 생성 시 CENTRAL `CUSTOMER_CALL_SCRIPT_LOCK.md`를 함께 적용한다. `scripts/customer_branch_engine.js`의 `prepareContactCopy`는 source-backed `copy_context`를 필수로 받는다. 일방 발송/실제 답변/견적/구매를 구분하며, 자료 추천 판정이 PASS여도 멘트 근거가 없으면 `VERIFY_COPY_EVIDENCE / HOLD`로 차단한다. 짧은 질문 후 고객의 범위 확인 전 발송으로 진행하지 않는다. 자동 품질 판정은 `DRAFT_VALIDATED`이며 실제 통화 평가나 일반 Chat 자동호출 COMPLETE가 아니다.

### 이메일 수집/검증
- 고객 발굴
- 기관/부서/이름/직책/이메일 검증
- 고객 DB 구축
- 발송표 정렬

### 고객 안내 통합
- 검증 고객의 실제 업무축 판단
- 과거 문의·견적·구매·회신 이력 확인
- 추천자료 선정
- 메일 제목·이메일 주소·필요 문안 작성
- 중간안내서/최종안내서 데이터 작성
- 발송용 최종 출력

이미 검증된 고객 이메일·이름·직책을 임의 추정·수정하지 않는다.
고객 안내는 신규 인력 탐색이나 신규 이메일 추정을 수행하지 않는다.

## 3. 고객 필드
공통 기본 필드는 다음 순서를 기준으로 한다.
- 고객번호/등록번호
- 기관
- 부서
- 이름
- 직책
- 담당업무
- 연구/사업 키워드
- 이메일
- 전화
- 검증결과
- 과거 문의/견적/구매/회신 이력
- 추가 메모

고객번호는 고객→추천자료→안내서→발송이력까지 유지한다.
입력값이 비어 있으면 추정하지 않고 공란 또는 HOLD로 둔다.

## 4. 시작점·중복·발송이력
- 고객번호 + 이름 + 이메일을 기본 중복키로 사용한다.
- 이미 발송한 고객과 보고서는 중복 차단한다.
- 사용자가 특정 고객부터 다시 작업하라고 하면 그 고객부터 시작하고 임의로 다음 고객으로 건너뛰지 않는다.
- 이전 대화창의 마지막 실제 작업지점이 지정되면 그 지점을 최우선 시작점으로 사용한다.
- 같은 고객에게 이미 제시한 동일 자료는 재추천하지 않는다.

## 5. 고객 판단 순서
1. 기관 실제 산업·사업 맥락
2. 기관의 현재 프로젝트·사업축
3. 고객 회사/기관 최신 사업·제품·연구·투자·조직 방향
4. 부서 기능
5. 실제 담당업무
6. 연구/사업 키워드
7. 과거 실제 문의·견적·구매·회신
8. 사용자 원문·추가 메모

### 금지
- 부서명 한 단어만 보고 일반 교육·관리·소프트웨어 보고서 추천
- 산업 일반론만으로 추천
- 일방 발송 이력을 실제 관심 이력보다 우선
- 고객 업무와 넓게만 겹치는 자료 추천

과거 실제 문의·구매·견적·회신은 일방 안내보다 우선한다.

### 5-A. 고객 방향 카드 / 제외축 정밀 필터 — 필수 내부 게이트
추천자료를 찾기 전에 고객마다 내부적으로 다음 6축을 고정한다.
1. 기관 산업축
2. 부서 기능축
3. 실제 담당업무축
4. 현재 연구·사업축
5. 향후 관심 방향축
6. 제외축

각 고객 카드에는 다음을 분리해 기록한다.
- 반드시 포함되어야 할 산업·기술 키워드
- 제외해야 할 비관련 산업·기술 키워드
- 담당업무에서 직접 연결되는 보고서 주제
- 담당업무와 연결되면 안 되는 보고서 주제

후보 보고서는 제목만 보지 않고 해당 상세페이지의 소개문, 목차, 핵심 세그먼트, 적용산업까지 고객 방향 카드와 대조한다.
선별은 `기관 산업 → 부서 기능 → 담당업무 → 세부 키워드 → 제외 키워드` 순서의 screen-out 필터로 수행한다.
- 제외 키워드나 연결 금지 주제에 걸리면 제목이 비슷해도 후보에서 제거한다.
- 포함 키워드가 약하고 넓은 산업 일반론만 겹치면 PASS하지 않는다.
- 제외축은 §5의 기존 판단 순서와 §6~§10의 검증을 대체하지 않고 추가 정밀 필터로 적용한다.

## 6. 추천자료 기본 3종
1. 핵심 맞춤 자료
2. 같은 기술/산업축의 유사 확장 자료
3. 기관 맥락에 직접 연결되는 안전 공통 자료

- 검증 가능한 후보를 다시 탐색해 3종 구성을 우선하되, 직접성·거래 발행사·상세페이지 검증 조건을 충족하지 못하면 억지로 채우지 않고 고객 작업을 HOLD한다.
- 같은 고객 안에서 동일·유사 보고서 중복 금지.
- 여러 고객에게 동일한 3종 세트 반복 금지.
- 기본 3종은 서로 다른 거래 발행사로 구성한다. 동일 발행사 중복은 금지한다.
- 동일 발행사 외에는 직접성·상세페이지 검증·최신 발행일 순으로 회피구조를 적용한다.
- 3종을 서로 다른 거래 발행사로 구성할 수 없으면 억지로 동일 발행사를 반복하지 말고 HOLD한다.

## 8. 선택 우선순위
1. 고객 직접성
2. 실제 상세페이지 검증
3. 최신 발행일
4. 발행사 분산
5. 재사용·중복 위험

최신이라는 이유만으로 직접성이 약한 자료를 올리지 않는다.
- 기본 추천 자료유형은 해외 시장보고서를 우선한다.
- 보고서 제목에 특정 지역·국가명이 포함된 지역 한정 타이틀은 기본 추천 후보에서 제외한다.
- 예: `North America`, `Asia Pacific`, `Europe`, `China`, `U.S.` 등 지역·국가 한정 제목은 사용자가 지역 보고서를 직접 요청한 경우에만 허용한다.
- 지역이 목차·세그먼트에 포함되는 것은 허용하되, 보고서 제목 자체가 특정 지역·국가 한정이면 제외한다.
- 공학도서·기술도서는 고객이 도서를 직접 요청했거나, 동일 주제의 검증 가능한 해외 시장보고서가 없고 기초원리·설계·공정 등 기술심화 자료가 고객 목적에 더 직접적인 경우에만 보조 후보로 사용한다.
- 국내 보고서는 사용자가 국내 자료를 명시적으로 요청한 경우에만 별도 분리하며, 일반 고객 안내 추천에서는 우선 후보로 사용하지 않는다.

## 9. 보고서 상세페이지 원문 전용 규칙 — 최상위 잠금
고객 안내용 보고서 데이터는 **해당 발행사의 실제 보고서 상세페이지에 현재 표시된 내용만** 사용한다.

허용:
- 실제 영문 제목
- 공식 한글 제목이 페이지에 있는 경우 그 제목
- 발행사
- 페이지 수
- 정가/라이선스 가격
- 발행일
- PDF 표시
- 같은 상세페이지의 Overview / Highlights / Segmentation / Table of Contents 등 공개 내용

금지:
- 검색결과 요약으로 값 확정
- 모델 지식으로 보충
- 다른 리셀러/사이트 값 혼합
- 임의 한글 번역을 공식 제목처럼 표시
- 임의 가격·페이지·발행일·목차 생성
- 보고서 페이지에 없는 설명을 보고서 내용처럼 표시
- 다른 보고서 목차 사용

페이지에 없는 값은 공란 또는 `확인 필요`로 둔다.

### 공급가격
공급가격은 발행사 페이지 원문 값이 아니라 내부 계산값이다. 사용자가 공급가격 계산을 명시적으로 요구하거나 별도 내부 가격규칙을 호출한 경우에만 계산한다. 그 외에는 공란/확인 필요.

## 10. 보고서 검증 게이트
각 자료마다 다음을 통과해야 한다.
- 실제 발행사 상세페이지 존재
- 출력 영문 제목 = 상세페이지 제목
- 발행사 일치
- 링크 정상
- 다른 보고서로 리디렉션되지 않음
- 발행일/페이지/가격은 페이지 표시값만 사용
- 공개 콘텐츠/목차는 같은 보고서 페이지에서 확인
- 최종안내서 목차는 발행사 상세페이지의 실제 Table of Contents 영역에서 상위목차와 그 바로 아래 하위목차 2단계만 사용한다.
- 하하위·하하하위는 제외하되, 상위·직접 하위 항목은 목차 시작부터 마지막 항목까지 자르거나 요약하지 않는다.
- Summary, Insights, Segmentation, Report Scope 등 TOC 밖의 영역을 목차로 재구성하면 FAIL이다.

하나라도 불명확하면 PASS 금지.

## 11. CUSTOMER_LINK_SANITIZE_GATE
고객에게 보이는 URL은 발행사 원문 상세페이지의 순수 URL이어야 한다.

제거/금지:
utm_source, utm_medium, utm_campaign, utm_term, utm_content, fbclid, gclid, mc_cid, mc_eid, _ga, _gl, chatgpt.com 관련 문자열, 검색엔진/리디렉션 중간 URL.

`?utm_source=chatgpt.com` 등 검색 흔적이 고객용 출력에 남으면 FAIL.

## 12. 고객별 최종 출력 시작 순서 — 절대 고정
실제 고객 작업 결과는 반드시 다음 두 줄로 시작한다.

`메일 제목: [해외시장자료 안내] {기관} {이름}님`
`이메일 주소: {검증된 실제 이메일}`

- 사용자가 다른 제목 형식을 직접 지정하면 최신 지시 적용.
- 이메일 추정 금지.

## 13. 안내서 직접 붙여넣기 순서 — 절대 고정
추천자료 1 → 2 → 3 순으로 아래 블록 반복.

### 추천자료 N
1. 영문 제목
2. 한글 제목
3. 도서정보 전체 형식
4. 자세한 내용의 링크
5. 중간안내서용 공식 공개 콘텐츠 또는 최종안내서용 실제 목차

### 도서정보 원본 형식
`◇ 발행사: {발행사} ({페이지} Pages)    ◇ 정가: {정가}`
`◇ 발행일: {발행일} -PDF-    ◆ 공급가격: {공급가격}`

- `◇`, `◆`, `-PDF-`, 통화기호 등 원본 기호 유지.
- 상세페이지에 없는 값 임의 생성 금지.
- 사용자가 데이터만 원하면 새 표 대신 위 순서의 순수 텍스트 블록 제공.

## 22. PASS / HOLD / FAIL
### PASS
- 시작점 정확
- 고객/자료 중복 없음
- 고객 실제 축과 직접 매칭
- 거래 발행사 기준 적용
- 실제 상세페이지 검증
- 임의 데이터 없음
- URL 정화 완료
- 안내서 순서/목차/복사 규칙 준수
- 고객번호 기존값 승계 및 중복 없음

### HOLD
- 직접성 높은 추천 3종을 거래 발행사·상세페이지 검증 조건까지 충족해 확보하지 못함
- 상세페이지 핵심값 미확인
- 링크 안정성 미확인
- 원본 렌더 검증 불가
- 분야 접두어 또는 기존 마지막 고객번호를 실제 DB에서 확인하지 못함

※ 거래 발행사 여부가 불명인 개별 자료는 §7에 따라 후보에서 즉시 제외한다. 그 자료 자체를 HOLD 후보로 남기지 않는다. 제외 후에도 검증 가능한 직접성 높은 3종을 구성하지 못할 때만 고객 작업을 HOLD한다.

### FAIL
- 시작 고객 임의 변경
- 무관 자료 추천
- 외부/제외 발행사 사용
- 제목-링크 불일치
- 임의 데이터 생성
- 다른 보고서 목차 사용
- 추적 URL 노출
- 안내서 순서/원본 구조 훼손
- 검증하지 않고 완료/PASS 선언
- 기존 고객번호를 새 번호로 재발급하거나 다른 고객에게 재사용

## 23. 실패 반복 방지
- 사용자가 지적한 실패 유형은 즉시 공통 규칙으로 승격.
- 실패 결과물을 다음 기준본으로 사용 금지.
- 같은 실패 방식을 반복하지 않는다.
- 사용자가 이미 설명한 규칙을 다시 설명하도록 요구하지 않는다.
- 같은 오류를 사용자가 다시 지적하면 기존 수정이 실제로 작동하지 않은 것으로 보고 원인을 다시 조사한다.

## 24. 통합 완전성 검증 프로토콜 — 필수
중앙마스터를 수정하거나 과거 규칙을 통합할 때 반드시 아래를 수행한다.

1. 관련 과거 대화기록/지시문/보완문서를 실제 내용으로 검색한다.
2. 규칙을 기능별로 분해한다: 고객판단 / 고객번호 / 추천 / 발행사 / 보고서 검증 / 메일 / 안내서 / 목차 / 링크 / 가격 / 출력 / 복사 / 스팸회피 / PASS-HOLD-FAIL.
3. 규칙 원장에 최소 `규칙 ID / 작업군 / 출처 / 원래 규칙 / 최신 여부 / GitHub 반영 여부 / 반영 위치 / 충돌 규칙 / 최종 규칙 / PASS-HOLD-FAIL`을 기록한다.
4. 각 과거 규칙에 대해 중앙마스터 대응 항목이 있는지 대조한다.
5. `반영 / 충돌로 대체 / 현재 지시로 폐기 / 미반영` 상태를 판정한다.
6. 미반영은 중앙마스터에 추가한다.
7. GitHub 파일을 실제로 수정하고 Commit SHA를 확인한다.
8. 수정 직후 GitHub에서 같은 파일을 다시 FETCH한다.
9. 원래 규칙 원장과 재조회 파일을 다시 항목별로 역대조한다.
10. 원본 규칙 수 / 최종 적용 규칙 수 / GitHub 반영 규칙 수 / 누락 규칙 수 / 충돌 미해결 수 / 잘못 삭제된 기존 규칙 수 / 최신 지적사항 미반영 수를 확인한다.
11. `누락 0 / 충돌 미해결 0 / 잘못 삭제 0 / 최신 지적 미반영 0`일 때만 통합 검증 완료로 판정한다.

GitHub 쓰기 성공 응답만으로 완료 처리하지 않는다. **재조회와 역검증이 필수다.**
과거 `FINAL`, `COMPLETE`, `LOCK`, `통합 완료` 표시는 증거로 사용하지 않는다.

## 25. 유지보수 잠금 및 Source of Truth
- 고객 안내 작업군의 유일한 Source of Truth는 이 `docs/UNIFIED_CUSTOMER_GUIDANCE_RULES.md`다.
- `CUSTOMER_WORKFLOW_MASTER.md`는 여러 고객업무 모드의 라우팅·공통 참조 문서이며 고객 안내 전용 규칙의 경쟁 중앙마스터로 취급하지 않는다.
- 고객 안내 전수검증 중에는 다른 작업군 중앙마스터를 수정하지 않는다.
- 다른 고객 안내 규칙 문서에 신규 규칙 추가 금지.
- 과거 규칙 문서는 참고·감사용.
- 새 고객 안내 공통 규칙은 이 문서 한 곳에만 통합.
- 사용자에게 과거 규칙을 반복 복사하도록 요구하지 않는다.

## 26. 분야별 영구 고객번호 — 기존번호 우선 잠금
- 고객번호는 분야별 영구번호이며 한 번 부여하면 변경·삭제·재사용·재배정하지 않는다.
- 고객 안내는 이메일 수집/기존 DB에서 넘어온 고객번호를 그대로 승계하고 새 번호를 다시 발급하지 않는다.
- 신규 입력에 번호가 없으면 먼저 기존 DB에서 `기관+이름`, `기관+이메일`, `이름+이메일`을 대조해 기존번호를 추적한다.
- 진짜 신규 고객이며 해당 분야 번호체계와 마지막 번호가 실제 자료로 확인된 경우에만 다음 미사용 번호를 부여한다.
- 분야 접두어를 추정하여 만들지 않는다.
- 현재 확인된 번호체계는 다음과 같이 관리한다.
  - 반도체: `SEM-###` — 실제 고객 안내 원문에서 확인됨.
  - 탄소·복합재: 기존 고객 안내 원문에 `C-###` 계열이 실제 사용 중이므로 기존 `C-###`를 보존한다. 기존 고객을 `CAR-###`로 일괄 변경하지 않는다.
  - 로봇: `ROB-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 방산: `DEF-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 조선/해양: `SHP-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 배터리: `BAT-###` — 기존 중앙 고객업무 규칙의 확정 계열을 승계한다.
  - 인공지능 및 그 밖의 분야: 기존 확정 번호체계가 실제 자료에서 확인되기 전에는 접두어를 임의 생성하지 않고 HOLD한다.
- 서로 다른 분야 고객은 섞지 않는다. 한 고객이 복수 분야와 관련되어도 원본 고객번호를 유지하고 분야 태그로 연결한다.

## 27. 통일 출력 스키마 및 세로 배치
- 고객 기본정보는 `고객번호 | 기관 | 부서 | 이름 | 직책 | 담당업무 | 연구/사업 키워드 | 이메일 | 전화 | 검증결과 | 추가메모`를 기본으로 통일한다.
- 추천자료는 고객 정보 바로 아래 별도 표/블록으로 배치한다.
- 가로로 긴 통합표 하나로 고객정보와 추천자료를 합쳐 스크롤을 유발하지 않는다.
- 추천자료 기본 컬럼은 `추천순위 | 제목 | 발행사 | 링크 | 추천 근거 키워드`다.
- 고객 1명 단위로 고객정보 → 추천자료 순서가 한눈에 이어져야 한다.
- 사용자가 특정 출력형식을 직접 지시하면 최신 직접 지시를 우선한다.

## 28. 껍데기 작업 FAIL 판정
다음은 고객 안내 중앙통합 완료로 인정하지 않는다.
- 통합문서만 작성하고 GitHub 미반영
- 제목/목차만 만들고 실제 규칙 본문 미반영
- 과거 원문을 실제로 읽지 않고 통합 선언
- 규칙 일부만 선택 통합
- 사용자 지적을 대화에서만 기억
- GitHub 수정 후 재조회하지 않음
- Commit 없이 반영 완료 보고
- 누락검사 없이 FINAL 표시
- 과거 FINAL 문서를 그대로 신뢰
- 사용자가 직접 검사해야 누락을 발견할 수 있는 상태

## 29. 완료 상태 보고 잠금
고객 안내 전수검증의 상태는 실제 실행 기준으로만 다음 중 하나를 사용한다.
- 실제 실행 완료
- 진행 중
- 아직 실행하지 않음
- 확인 필요

## 42. 사용자 추가 지적 0회 목표·소형 관찰자 연속교정 잠금 — 2026-08-22

- 사용자 지적 횟수를 학습 반복 횟수로 요구하지 않는다. 정상 목표값은 항상 `추가 사용자 지적 = 0회`다.

## 44. 최종 사용자 화면 동일성·전항목 판정·오판정 방지 잠금 — 2026-08-22
- 게이트가 검증한 `actual output fixture`와 사용자에게 실제 보여주는 안내서 본문 사이에 **모델 재요약·재편집·목차 축약·하위목차 삭제·문구 재작성** 단계를 두지 않는다. PASS된 fixture를 최종 화면에서 다시 줄이면 그 자체로 `USER_VISIBLE_OUTPUT_DIVERGED` FAIL이다.
- 김명곤 직전 사례에서 actual fixture에는 추천 1·2·3의 하위목차가 존재했는데 최종 응답에서 상위목차 위주로 다시 줄인 것은 게이트 PASS 이후의 **출력 우회 오류**이며, 직전 PASS 보고는 무효로 판정한다. 하위목차가 원문 오류라서 삭제된 것이 아니며, 원문 재검증 없이 임의 삭제할 수 없다.
- 목차 검증은 일부 필수 줄+최소 줄수 방식으로 PASS하지 않는다. expected의 `toc_lines`는 해당 고객에게 출력할 **전체 공개 2단계 목차**여야 하고 actual 목차와 `줄 수 / 각 줄 원문 / 순서 / 번호 / 들여쓰기 / 하위목차 수 / 마지막 항목`을 모두 exact 대조한다.
- `toc_match_mode=required`, `toc_min_lines`처럼 일부 줄만 맞으면 통과하는 느슨한 검증은 최종 고객출력 PASS 판정에 사용하지 않는다.
- 목차 번호 검사는 실제 번호 문자열을 expected와 actual에서 각각 추출해 비교한다. 작동하지 않는 조건식이나 자기모순 조건식으로 번호 PASS를 만들면 게이트 결함으로 판정한다.
- 각 고객 출력 전 근거보고에는 최소 다음 항목을 **각각 독립 행으로 PASS / FAIL / HOLD** 표시한다: `추천자료 3종 수`, `공식 영문 전체 타이틀`, `한글 전체 번역`, `발행사 공식명`, `페이지`, `정가`, `발행일`, `도서정보 1행`, `도서정보 2행`, `출력 URL 원문 일치`, `저장/출력 URL 추적파라미터 없음`, `클릭 후 런타임 URL 추적파라미터 여부`, `TOC 원문 출처`, `TOC 전체 줄 수`, `TOC 모든 하위목차 존재`, `TOC 번호 복사 가능`, `TOC 들여쓰기`, `TOC 마지막 항목`, `보고서 정보 라벨 분리`, `보고서 정보 원문 수치 번역 일치`, `최종 사용자 화면 = 검증 fixture 동일성`.
- 위 항목 중 하나라도 검증하지 않았으면 PASS가 아니라 HOLD 또는 확인 필요다. 일부만 검사하고 전체 PASS라고 묶어 보고하지 않는다.
- 링크는 두 단계로 분리 판정한다. `저장/출력 URL` 자체에 `utm_source`, `utm_*`, `chatgpt.com` 등이 없으면 `STORED_URL_CLEAN=PASS`다. 그러나 ChatGPT UI가 클릭 시 런타임에 추적 파라미터를 덧붙이는지 실제 클릭 결과를 도구로 검증하지 못했다면 `CLICK_RUNTIME_URL_CLEAN`은 PASS로 추정하지 않고 `확인 필요/HOLD`로 표시한다.
- 제품 UI가 클릭 시 자동으로 추적 파라미터를 붙이는 경우는 fixture 문자열 오류와 구분해 보고한다. 고객에게 복사해 사용할 텍스트 URL은 항상 추적파라미터 없는 순수 URL로 유지한다.
- 추천 1에서 원문 재검증으로 하위목차가 실제 없다고 새로 확인된 경우에만 expected와 actual을 함께 수정한다. 그 전에는 이미 검증 fixture에 존재하는 하위목차를 임의 삭제하지 않는다.
- 추천 2 Technavio는 전체 공개 하위목차를 중간 생략하지 않고 `16.10 List of abbreviations`까지 모두 존재해야 PASS다. `16.10`만 마지막에 붙여놓고 8~16장의 중간 하위목차를 삭제한 출력은 FAIL이다.
- 추천 3도 동일 기준을 적용한다. 3종 존재만 PASS여도 제목·도서정보·URL·목차 전체·하위목차·번호·마지막 항목·보고서 정보 중 하나라도 FAIL/HOLD면 자료 3 또는 전체 안내서를 PASS로 보고하지 않는다.
- 범용 출력게이트는 `checks[]` 형태의 전항목 판정 근거를 반환하고, 사용자 보고표는 그 결과를 축약 없이 항목별로 대응시킨다.
- 이전 PASS가 실제 사용자 화면과 불일치한 사실이 발견되면 즉시 `이전 PASS 오판정`으로 정정하고, 사용자가 다시 지적할 때까지 기다리지 않고 마스터·expected·게이트·actual·최종화면 경로를 연속 교정한다.

## 45. 느슨한 검증 영구 차단·단일 릴리스 경로 구조 잠금 — 2026-08-22
- 이 조항은 §40·§44보다 우선하는 최종 구조 잠금이다. 같은 취지의 규칙을 다시 설명하는 것이 아니라 **느슨한 검증과 PASS 후 재작성 경로 자체를 제거**하는 실행 규칙이다.
- 최종 고객출력용 expected는 반드시 `validation_contract: STRICT_FULL_V1`을 가져야 한다. 없거나 다른 값이면 즉시 FAIL한다.
- 보고서별 목차 expected는 반드시 `toc_contract: EXACT_FULL`을 가져야 하며, `toc_match_mode`, `toc_min_lines`, 일부 필수 줄만 확인하는 방식은 최종 출력에서 금지하고 존재 자체를 FAIL로 처리한다.
- expected의 `toc_lines`는 실제 공개된 상위+직접 하위 전체목차의 **완전한 배열**이어야 한다. 전체목차가 아닌 샘플·시작/끝 표식·부분 목록은 expected로 사용할 수 없다.
- 최종 사용자에게 보일 본문은 검증 전에 하나의 고정 actual 파일로 생성하고, 그 파일 전체의 SHA-256을 `user_visible_output_sha256`에 저장한다. 이 64자리 해시가 없으면 게이트는 PASS할 수 없다.
- 게이트는 actual 전체본문의 SHA-256과 `user_visible_output_sha256`을 마지막 단계에서 반드시 exact 비교한다. 제목·목차·하위목차·줄바꿈·문구를 PASS 후 한 글자라도 바꾸면 `USER_VISIBLE_OUTPUT_EXACT=FAIL`이다.
- 사용자에게 실제 보여줄 안내서 본문은 **오직 `--emit-if-pass`가 방출한 actual 원문 그대로** 사용한다. 게이트 PASS 후 모델이 다시 요약·재작성·Markdown 재구성·목차 축약하는 별도 경로를 금지한다.
- 게이트에는 자체 회귀검사를 유지한다. 최소 `정상 전체본 PASS / 하위목차 1줄 삭제 FAIL / 추적 URL 추가 FAIL / 추천자료 3 누락 FAIL / 느슨한 toc_match_mode 존재 FAIL / 사용자화면 해시 누락 FAIL`을 자동검사해야 한다.
- 자체 회귀검사가 PASS하지 않으면 실제 고객검증을 시작하지 않는다. 실제 고객검증이 PASS하지 않으면 사용자 출력으로 넘어가지 않는다.
- 사용자 보고표는 게이트 `checks[]`를 근거로 만들고 임의로 PASS를 추가하지 않는다. 게이트에 항목이 없으면 그 항목은 PASS가 아니라 HOLD/미검증으로 보고한다.
- 구조 순서는 `원문 검증 → 전체 expected 작성 → 고정 actual 작성 → actual 해시 잠금 → 게이트 자체검사 → 실제 actual/expected 전항목 검사 → checks[] 근거표 → --emit-if-pass 원문 출력`으로 고정한다.
- 이 구조에서 중간 어느 단계라도 FAIL이면 사용자의 추가 지시를 기다리지 않고 소형 관찰자가 원인을 수정한 뒤 처음부터 다시 검증한다. FAIL 상태의 안내서나 부분 축약본을 사용자에게 보여주지 않는다.
- 김명곤 fixture에 과거 `toc_match_mode`, `toc_min_lines`, 부분 `toc_lines`가 남아 있으면 현재 구조에서는 **의도적으로 FAIL**되어야 한다. 이를 PASS시키기 위해 게이트를 느슨하게 되돌리는 것을 금지한다. 먼저 expected를 전체 목차 exact 형식으로 복구한 뒤 재검증한다.

## 48. 최종안내서 목차 누락 금지·보고서정보 원문 위치 표시 잠금 — 2026-09-02
- 최종안내서로 출력하는 각 추천자료에는 **목차가 반드시 존재**해야 한다. `목차:` 라벨만 있고 실제 TOC 줄이 없거나, 제목·도서정보·링크·보고서정보만 출력하고 목차를 생략하면 `TOC_MISSING_IN_FINAL_GUIDE`로 FAIL 처리한다.
- 목차는 기존 §35·§40·§44·§45·§46 규칙대로 원 발행사 상세페이지의 실제 Table of Contents에서 상위+직접 하위 2단계를 처음부터 마지막 공개 항목까지 모두 출력한다. 목차를 검증했다는 이유만으로 사용자 화면에서 생략할 수 없다.
- 사용자가 안내서 전체 재출력을 요구한 경우 `메일 제목/이메일 → 추천자료 1·2·3 → 각 자료의 전체 타이틀 → 도서정보 2줄 → 순수 링크 → 실제 목차 전체 → 보고서 정보` 순서를 최종 사용자 화면에서도 그대로 유지한다.
- `보고서 정보:`는 기존처럼 원 발행사 상세페이지의 수치 포함 원문 한 문장 또는 짧은 연속 문단을 한국어로 직역하되, 그 아래 또는 같은 블록에 **원문 위치:**를 추가한다.
- `원문 위치:`에는 사용자가 해당 페이지를 열었을 때 실제 찾을 수 있도록 페이지 내 섹션/헤딩명을 그대로 적는다. 예: `원문 위치: Report Highlights`, `원문 위치: Market Insights`, `원문 위치: Executive Summary`. 발행사 페이지에 명확한 섹션명이 없으면 `원문 위치: 상세페이지 상단 소개문`, `원문 위치: TOC 아래 시장개요 영역`처럼 실제 위치를 과장 없이 설명한다.
- `원문 위치:`를 표시할 때 검색결과 요약·리셀러·다른 페이지 위치를 쓰지 않는다. 반드시 해당 추천자료의 원 발행사 상세페이지에서 실제 확인한 위치만 적는다.
- 보고서 정보 원문 위치를 확인하지 못하면 임의 추정하지 않고 `원문 위치: 확인 필요`로 둔다. 위치가 확인되지 않은 상태에서 전체 PASS로 보고하지 않는다.
